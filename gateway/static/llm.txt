# Agent Middleware API — LLM-Readable Documentation

**Agent-first:** You are the intended reader. This file is primary prose for autonomous agents and orchestrators. Before acting, fetch `GET /.well-known/agent.json`, then check `GET /health/dependencies` before assuming real side effects: HTTP 200 alone does not mean every dependency is ready.

**Version:** use `version` from `GET /.well-known/agent.json` (this document may be cached).
**Base URL:** {{PUBLIC_URL}}
When served, this token is replaced with the configured `PUBLIC_URL`. If unset, the response asks operators to configure it; `http://localhost:8000` is only a local example.
**Auth:** `X-API-Key` header on protected routes

## What This API Does

Agent Middleware API is a **transaction-integrity boundary for consequential
autonomous actions**. On the supported upstream-MCP path, one logical action
binds scoped authority and configured consumption to at most one gateway
dispatch and debit, explicit `delivery_uncertain`, and linked gateway evidence.

This is a durable gateway state machine, not one distributed ACID transaction
or proof of the downstream effect. IAM, budget controls, receipts, and audit
chains are supporting mechanisms rather than separate product wedges.

An accepted idempotency key binds one immutable invocation. Reusing that key
with different tool input fails closed with an idempotency conflict; use a new
key for each new invocation.

On `POST /mcp/messages` that conflict is HTTP 200 with a JSON-RPC error.
Match `error.message` `idempotency_key_reused`. The code on that message is
-32603, which is also used for `internal_error`, so the message is the
signal, not the code alone. The same route reports `idempotency_in_progress`
as HTTP 200, code -32005, message `idempotency_in_progress`. Retry that same
key. `delivery_uncertain` also uses code -32005, but means dispatch may have
occurred: inspect the receipt and audit record and reconcile the downstream
outcome before deciding on another action. Match the message, not only the
code. This route does not report either idempotency condition as HTTP 409.
REST routes such as
`POST /v1/permits` do use HTTP 409 for an idempotency conflict and for a key
that is still in progress.

The product loop is:

```text
logical action -> authorize -> reserve allowance -> debit -> claim dispatch
-> confirmed outcome | delivery_uncertain -> receipt/audit
-> authoritative external reconciliation required
```

Read `agent_first.positioning` on `GET /.well-known/agent.json` for the
versioned product category, transaction semantics, and claim boundary.

Supporting infrastructure:
- **Identity & authority** — Wallet-scoped agents, API keys, and scoped permits
- **Logical action** — Accepted idempotency key plus payload binding
- **Execution state** — One-shot gateway dispatch and explicit uncertainty
- **Configured accounting** — Wallet credits/call allowance and replay without double debit
- **Evidence** — Signed receipts and audit linkage for external reconciliation
- **Readiness** — `/health/dependencies` (dependency truth for the selected tool)

## Quick Start for Agents

### 1. Discover What This API Offers

```bash
GET /.well-known/agent.json
GET /llms.txt
GET /mcp/tools.json
GET /openapi.json
```

On production-like boots, GET /mcp/tools.json requires an operator-issued key and returns 401 without one. Local quickstart stays anonymous. GET /.well-known/agent.json, GET /llms.txt, and GET /openapi.json stay unauthenticated.

`GET /llm.txt` remains available as a backward-compatible alias.

Use `/v1/discover` as an optional expanded catalog after the bootstrap sequence.
Treat `/mcp/tools.json` as authoritative for callable MCP tools.
Before invoking, inspect the `/health/dependencies` JSON body: HTTP 200 alone
does not mean every dependency is ready. Health never replaces authentication,
permit authorization, or receipt verification.

### 2. Get Operator-Provisioned Access

There is no public signup or unauthenticated key mint. The operator provisions
the sponsor/partner wallet, wallet-scoped API key, credits, and permit. Pass the
key as `X-API-Key: your-key` on every protected request.

### 3. Inspect the Published Live Proof

The human site publishes one non-sensitive portable `partner.echo` receipt and
the matching public-key snapshot:

```bash
GET https://www.agentmiddleware.dev/proof/receipt.json
GET https://www.agentmiddleware.dev/proof/trust-keys.json
```

Use the offline CLI command on `https://www.agentmiddleware.dev/proof/`. A valid
signature proves the receipt matches the supplied snapshot. Authenticate or
pin that snapshot through a trusted channel before treating issuer identity as
independently established.

### 4. Governed Tool Loop

Register one real partner tool through the operator path, then:

```bash
# Issue a scoped permit for that tool
POST /v1/permits
{"wallet_id": "...", "allowed_tools": ["partner.tool"], ...}

# Invoke via MCP with permit + idempotency key
POST /mcp/messages
{"jsonrpc":"2.0","method":"tools/call","params":{...}}

# Export the signed receipt for offline verification
GET /v1/receipts/{receipt_id}/portable
```

`partner.notes.write` is a local-only dogfood fixture. Production keeps
`ENABLE_DOGFOOD_TOOL=false`; do not use that fixture as evidence of a partner
integration.

The default available governed transport is `POST /mcp/messages`, a
project-specific legacy JSON-RPC endpoint that does not implement standard MCP
initialization. An operator may enable the standards-compliant Streamable HTTP
transport at `POST /mcp`; do not assume that endpoint is available unless the
deployment's discovery manifest lists it.

## Billing & Pricing

### Credit System
- Credits are a closed-loop metering unit for the pilot, not payment rails.
- There is no public pricing tier, free-credit grant, SLA, or settlement claim.
- Operators provision partner credits; public self-serve top-up is out of scope.

### Rate Limits
- Default: 120 requests/minute per API key, configurable by the operator.
- No extra burst allowance. Check `/v1/discover` rate-limit metadata for the current limit.
- Requests without accepted credentials, including unauthenticated requests and rejected credentials, also count against a shared per-client pre-authentication bucket.
- Shared Redis counts fixed 60-second windows. The in-memory limiter, used when Redis is not configured or when a non-production boot loses Redis, counts a rolling 60 seconds.
- On a production-like boot with `REDIS_URL` set, a Redis outage does not use that in-memory limiter. Requests subject to rate limiting fail with HTTP 503 and error `rate_limiter_unavailable`; exempt public documentation and health routes are not refused by the limiter.

### Velocity Monitoring
Default velocity alert thresholds are 1000 credits per hour and 10000 credits
per day. The operator can change those defaults; a wallet's `hourly_limit` and
`daily_limit` override them. Velocity alerts are not a spending allowance.
When a wallet sets `daily_limit`, billing also enforces it as a hard cap:
an attempted charge above that cap is refused without debit, including when
`daily_limit` is zero.

The monitor records proposed spend before checking whether it is strictly
over a velocity threshold; equality is not a crossing. It checks the prior
alert count before adding the new alert. A first crossing does not itself
freeze the wallet, but another billing check can still deny the charge. With
`VELOCITY_FREEZE_THRESHOLD` at its default 3, a fourth over-limit assessment
after three recorded alerts requests a freeze; this is not necessarily the
fourth paid charge. The freeze assessment is not debited. Hourly and daily
spend counters roll over, but the alert count does not. Closed or suspended
wallets are not changed to frozen. If a governed database transaction rolls
back, its uncommitted velocity and billing mutations roll back with it. A
governed refusal can still commit an alert; a post-dispatch
`delivery_uncertain` outcome retains the debit.

## SDKs

Prefer the configured-upstream HTTP transaction loop above (logical action →
permit → MCP invoke → receipt/audit → authoritative external reconciliation).
Client libraries are optional and not required for the transaction-integrity
boundary.

### Python SDK (source checkout and release artifacts)

Install the SDK from source in `sdk/python/`. The agent manifest's
`integrations.python_sdk` reports both the source version and the available
release tag; do not infer a package-index install from this document. The SDK
is **not** published to PyPI. Install from a clone of
https://github.com/agentmiddleware/agent-middleware (repository root):

```bash
pip install -e ./sdk/python
```

```python
from b2a_sdk import AgentMiddlewareClient

async with AgentMiddlewareClient(api_key="...", base_url="...") as client:
    tools = await client.discover_tools()
    result = await client.invoke_tool(
        tools[0].name,
        {"input": "..."},
        wallet_id="...",
        permit_id="...",
        idempotency_key="caller-owned-key",
    )
```

### TypeScript

No published TypeScript SDK. Use `/mcp/messages` only with a project-specific
JSON-RPC client, plus `/v1/permits` and `/v1/receipts`; standards-compliant MCP
clients require `/mcp` after the operator enables the Streamable HTTP transport.

## Error Codes

HTTP responses can report authentication, rate-limit, and REST failures.
These codes do not describe every governed failure on `POST /mcp/messages`:

| Code | Meaning |
|------|---------|
| 401 | Missing credentials, a malformed or too-short API key, or invalid bearer authentication. |
| 403 | A well-formed API key was rejected, or an HTTP route denied required wallet, tenant, administrator, policy, or ACL access. |
| 429 | A rate limit was exceeded: per-key, shared per-client pre-authentication (including unauthenticated requests and rejected credentials), or public MCP client/global bucket. |
| 503 | On a rate-limited request in a production-like boot with `REDIS_URL` set, the shared limiter could not use Redis. The error is `rate_limiter_unavailable`. |
| 500 | Unclassified server error on a REST route. |

`POST /mcp/messages` `tools/call` reports governed failures as HTTP 200 JSON-RPC errors. Do not branch on HTTP 402 or HTTP 409 for that route. Read `error.message`:

| error.message | JSON-RPC code | Meaning |
|---------------|---------------|---------|
| insufficient_funds | -32004 | Billing refused the debit, including insufficient credits or a spending cap. |
| wallet_frozen | -32003 | Wallet is frozen. |
| wallet_expired | -32003 | Wallet is expired. |
| idempotency_key_reused | -32603 | Same key, different tool input. Match the message. This code is also used for `internal_error`. |
| idempotency_in_progress | -32005 | Same key is still in progress. Retry the same key. This code is also used for other retryable contention, so match the message. |
| delivery_uncertain | -32005 | Dispatch may have occurred. Inspect receipt and audit evidence, then reconcile the downstream outcome; do not treat it as an in-progress retry. |

Some REST billing routes report billing refusals, including insufficient
credits or spending caps, as HTTP 402. `POST /v1/permits` reports an
idempotency conflict as HTTP 409. On `POST /mcp/messages`, read the JSON-RPC
error body instead.
